# select와 스레드 풀이 뒤집히는 지점 (Apache Bench)

이 문서를 읽으면 동시 연결이 몇 개일 때부터 스레드 풀이 select보다 빨라지는지, 그때 각 서버가 CPU를 얼마나 쓰는지 알 수 있어요.
같은 조건으로 다시 측정하는 방법도 함께 적었어요.

측정일: 2026-11-25
앞선 측정: [동시성 방식별 성능 비교](benchmark.md)

## 1. 결론

| 동시 연결 수 | 더 빠른 쪽 | select 서버 CPU |
| --- | --- | --- |
| 1개 ~ 3개 | select | 59% → 84% → 97% |
| 4개 | 거의 같음 (5번 측정값의 범위가 겹침) | 98% |
| 5개 이상 | 스레드 풀 | 98% |

- **select는 동시 연결 3개부터 코어 하나를 다 써요.** 서버 CPU가 97%에 닿고, 처리량은 약 27,000 req/s에서 더 오르지 않아요.
- **스레드 풀은 동시 연결 4개일 때 select와 같아지고, 5개부터 확실히 앞서요.**
- 두 시점이 다른 이유는 요청 하나를 처리하는 데 드는 CPU 시간이에요. 스레드 풀은 약 60µs, select는 약 36µs예요. 스레드 풀이 select와 같은 처리량을 내려면 코어를 1.7개쯤 써야 하는데, 그 지점이 동시 연결 4개예요.
- select의 한계는 감시 비용이 아니라 코어 하나라서, `epoll`로 바꿔도 빨라지지 않을 거예요. 대신 select 루프를 프로세스 여러 개로 나누면(nginx 방식) 처리량이 오를 수 있어요. (6장, 측정하지 않은 판단)
- 80번 측정 모두 실패 요청과 2xx가 아닌 응답은 0개였어요.

## 2. 왜 다시 쟀나

[앞선 측정](benchmark.md)에서는 동시 연결 1개일 때 select가, 10개일 때 스레드 풀이 빨랐어요.
그 사이(2개~9개)를 재지 않아서 어디서 뒤집히는지 몰랐어요.

측정 전에 앞선 결과로 어림했을 때는 "select는 2~3개에서 코어를 다 쓰고, 스레드 풀은 3개쯤부터 앞선다"였어요.
select에 대한 어림은 맞았지만, 스레드 풀이 앞서는 시점은 어림보다 늦었어요. (5장 참고)

## 5. 해석

### select: 동시 연결 3개부터 코어 하나가 다 차요

- 동시 연결이 1개일 때 서버 CPU는 59%예요. 서버가 응답을 보낸 뒤 ab가 응답을 처리하고 새 연결을 맺는 동안 서버는 놀아요.
- 동시 연결이 늘면 다른 연결의 요청이 그 빈 시간을 메워요. 3개에서 97%가 되고, 그 뒤로는 처리량이 약 27,600 req/s에서 그대로예요.
- 요청 하나에 드는 CPU 시간은 동시 연결 1개일 때 48.9µs, 3개 이상에서는 35.5µs쯤이에요. 연결이 하나뿐이면 `select`를 한 번 부를 때 처리할 연결도 하나라서 요청당 비용이 커요. 연결이 많으면 한 번에 여러 개를 처리해서 비용이 줄어요.

### 스레드 풀: 요청 하나에 CPU를 더 쓰지만, 코어를 여러 개 써요

- 요청 하나에 드는 CPU 시간이 동시 연결 수와 상관없이 약 60µs예요. select(35.5µs)의 1.7배예요. main이 연결을 sbuf에 넣고, worker를 깨우고, mutex와 세마포어를 거치는 비용이 요청마다 더해져요.
- 대신 worker 4개가 코어 여러 개에서 함께 일해서, 동시 연결이 늘수록 쓰는 CPU가 늘어요. (57% → 97% → 135% → 166% → …)
- select와 같은 처리량(약 27,400 req/s)을 내려면 27,400 × 60µs ≈ 코어 1.65개가 필요해요. 스레드 풀이 166%를 쓰는 동시 연결 4개에서 두 방식이 같아지고, 그 뒤로는 스레드 풀이 앞서요.

### 어림이 빗나간 이유

측정 전에는 스레드 풀의 처리량이 동시 연결 수에 비례해서 늘 거라고 보고 "3개쯤부터 앞선다"고 어림했어요.
실제로는 1개일 때보다 2개일 때 1.8배, 3개일 때 2.4배만 늘었어요.
worker 수만큼 그대로 빨라지지 않았고, 요청당 비용도 select보다 커서 앞서는 시점이 4~5개로 늦어졌어요.

## 6. select를 더 빠르게 하려면

이 절은 구현하거나 측정한 내용이 아니에요. 위 측정 결과로 판단한 내용이에요.

### epoll로 바꿔도 이 조건에서는 빨라지지 않아요

`select`는 부를 때마다 감시하는 fd 목록 전체를 커널에 넘기고, 커널은 그 fd를 하나씩 확인해요. 그래서 감시하는 연결이 많을수록 비용이 커지고, fd 번호도 `FD_SETSIZE`(1024)를 넘을 수 없어요.
`epoll`은 감시할 fd를 커널에 한 번만 등록하고, 준비된 fd만 돌려받아요. 연결이 많아져도 감시 비용이 거의 늘지 않아요.

하지만 이 서버에서는 감시 비용이 병목이 아니에요.

- 요청 하나에 드는 CPU 시간이 동시 연결 3개일 때 35.8µs, 10개일 때 35.4µs로 거의 같아요. 감시하는 연결이 늘어도 비용이 늘지 않았어요.
- [앞선 측정](benchmark.md)에서 동시 연결 10개부터 200개까지 처리량이 약 27,000 req/s로 그대로였어요. (26,493 ~ 27,376)
- select의 CPU는 동시 연결 3개부터 98%예요. 코어 하나를 다 써서 더 빨라질 수 없어요.

`epoll`도 스레드 하나에서 돌면 코어를 하나만 써요. 그래서 동시 연결 200개까지는 바꿔도 처리량이 거의 그대로일 거예요.
`epoll`이 효과를 보는 건 연결이 수천 개 이상으로 많고, 그중 대부분이 놀고 있을 때예요.

### 이벤트 루프를 프로세스 여러 개로 나누면 처리량이 오를 수 있어요 (nginx 방식)

같은 select 서버를 프로세스 여러 개로 띄우고, 모두 같은 포트에서 듣게 해요. 새 연결이 오면 커널이 그중 하나에 나눠 줘요.
프로세스마다 select 루프가 따로 돌아서 코어를 여러 개 써요. nginx가 이 구조예요. (`worker_processes`, `listen ... reuseport`)

```
                         커널
클라이언트 연결 ──> [포트 8080] ──┬─> listen 소켓 1 → 프로세스 1 (select 루프)
                     해시로 분배  ├─> listen 소켓 2 → 프로세스 2 (select 루프)
                                 ├─> listen 소켓 3 → 프로세스 3 (select 루프)
                                 └─> listen 소켓 4 → 프로세스 4 (select 루프)
```

- **`SO_REUSEPORT`로 한 포트에 listen 소켓을 여러 개 열어요.** 보통은 같은 포트에 두 번째로 `bind`하면 `EADDRINUSE`로 실패해요. 이 옵션을 켜면 같은 사용자의 소켓 여러 개가 같은 포트를 쓸 수 있어요. 커널은 새 연결마다 (보내는 IP, 보내는 포트, 받는 IP, 받는 포트)를 해시해서 소켓 하나를 골라요. (리눅스 3.9부터)
- **listen 소켓은 `fork` 다음에 프로세스마다 따로 열어요.** fork 전에 하나만 열어서 같이 감시하면, 연결 하나에 모든 프로세스가 깨어나 `accept`를 다퉈요(thundering herd). 지금처럼 listen 소켓이 blocking이면 진 프로세스는 `accept`에서 멈추고, 그동안 맡은 다른 연결도 처리하지 못해요.
- **select 루프 코드는 그대로예요.** 프로세스마다 자기 `pool`을 가지고, 공유하는 메모리가 없어서 lock도 필요 없어요. 바뀌는 곳은 listen 소켓을 여는 부분과 main의 `fork`예요.

처리량이 오를 거라고 보는 이유는 요청당 CPU 시간이에요.

| | 요청 하나에 드는 CPU | 쓰는 코어 |
| --- | --- | --- |
| select (측정) | 약 36µs | 1개 |
| 스레드 풀 (측정) | 약 60µs | 여러 개 |
| select 프로세스 4개 (예상) | 약 36µs | 4개 |

스레드 풀은 main이 연결을 받아 worker에게 넘기는 비용 때문에 요청당 CPU를 select의 1.7배 써요.
select 프로세스 여러 개는 각자 직접 `accept`해서 넘기는 비용이 없어요. 그래서 코어마다 select만큼 효율을 내면 스레드 풀보다 처리량이 높을 가능성이 커요.

다만 코어 4개라고 처리량이 4배(약 110,000 req/s)가 되지는 않을 거예요.

- 연결을 맺고 끊는 커널 비용은 프로세스를 나눠도 그대로예요.
- ab 하나로 낼 수 있는 부하에도 한계가 있어요. 이번 측정에서 ab는 36,000 req/s를 낼 때 CPU를 84% 썼어요. 그보다 높은 처리량을 재려면 ab를 여러 개 동시에 돌려야 해요.

조심할 점도 있어요.

- **부하가 아니라 해시로 나눠요.** 한 프로세스가 느린 요청(CGI 등)을 처리하는 동안에도, 해시가 그 프로세스를 고르면 새 연결은 거기서 기다려요. 다른 프로세스가 놀고 있어도 일을 가져가지 않아요.
- **종료 처리가 필요해요.** 부모만 종료되면 자식들이 포트를 쥔 채 계속 돌아요. 부모가 종료 시그널을 자식들에게 전하고 `waitpid`로 회수해야 해요.

## 7. 한계

- **한 머신에서 측정했어요.** ab와 서버가 같은 WSL 가상 머신에서 돌아요. 절대값보다 두 방식 사이의 상대 비교로 봐야 해요.
- **뒤집히는 지점은 환경에 따라 달라요.** 요청당 비용의 비율(약 1.7배), worker 수, 서버에 준 코어 수, 응답 크기가 바뀌면 지점도 바뀌어요.
- **스레드 풀은 동시 연결 10개에서도 CPU를 217%만 써요.** 코어 4개를 다 쓰지 않는데도 [앞선 측정](benchmark.md)에서 약 41,000 req/s에서 멈췄어요. `accept`를 main 스레드 하나가 하는 것이 원인일 수 있지만, 이번 측정으로는 확인하지 않았어요.
- **ab도 CPU를 꽤 써요.** 스레드 풀을 잴 때 ab CPU가 84%까지 올라갔어요. 앞선 측정에서 ab 하나로 41,000 req/s 넘게 나왔으니 동시 연결 10개까지의 결과를 ab가 막지는 않았다고 봐요. 하지만 동시 연결이 더 많은 조건에서는 ab도 한계에 가까워져요.
- **CPU 사용률은 프로세스 전체를 합친 값이에요.** 스레드 풀에서 main 스레드와 worker가 각각 얼마나 썼는지는 나누지 않았어요.

## 8. 다시 측정하기

부록의 스크립트를 WSL에서 실행해요. 두 브랜치를 `git archive`로 `/tmp/benchx/`에 꺼내 빌드해요. 지금 작업 중인 브랜치나 파일은 건드리지 않아요.

```bash
sudo apt install -y apache2-utils      # ab가 없으면
git fetch origin                       # 팀원 브랜치를 최신으로 (Windows 쪽에서 실행해도 됨)
bash bench_cross.sh                    # 기본값: 10초 x 5회, 동시 연결 1·2·3·4·5·6·8·10개
```

설정은 [앞선 측정](benchmark.md)의 `bench3.sh`와 같은 환경 변수(`DUR`, `REPEAT`, `CS`, `FILE`, `REST`, `SERVER_CPUS`, `AB_CPU`)로 바꿔요. `CS`의 기본값만 `"1 2 3 4 5 6 8 10"`으로 달라요.

스크립트 맨 위의 `REPO`는 저장소의 WSL 경로예요. 자기 환경에 맞게 바꿔요.
두 방식 x 동시 연결 8종류 x 5번 = 80번 측정에 약 19분 걸려요.
끝나면 조건별 중앙값, 최소, 최대, CV, 서버 CPU, ab CPU 표를 출력하고, 원본은 `/tmp/benchx/results.csv`에 남겨요.

<details>
<summary>부록: bench_cross.sh</summary>

```bash
#!/usr/bin/env bash
# select와 스레드 풀이 뒤집히는 동시 연결 수를 찾는다. 서버와 ab의 CPU 사용률도 함께 잰다.
# 조건은 bench3.sh와 같다 (시간 기준, 반복, 순서 섞기, taskset, 접속 주소 바꾸기).
#   DUR=10 REPEAT=5 CS="1 2 3 4 5 6 8 10" bash bench_cross.sh
REPO="/mnt/c/Users/dhrho/문서/JungleGithub/mini-web-server"
B=/tmp/benchx
DUR=${DUR:-10}
REPEAT=${REPEAT:-5}
CS=${CS:-"1 2 3 4 5 6 8 10"}
FILE=${FILE:-home.html}
REST=${REST:-3}
SERVER_CPUS=${SERVER_CPUS:-0-3}
AB_CPU=${AB_CPU:-6}
OUT=${OUT:-$B/results.csv}
TCK=$(getconf CLK_TCK)

NAMES=(select threadpool)
declare -A REF=([select]=origin/con-io-multiflexing [threadpool]=con-thread-pool)
declare -A PORT=([select]=18502 [threadpool]=18503)
declare -A PID

command -v ab >/dev/null || { echo "ab가 없어요"; exit 2; }
pkill -x tiny 2>/dev/null
rm -rf "$B" && mkdir -p "$B"

for k in "${NAMES[@]}"; do
    mkdir -p "$B/$k"
    git -c safe.directory='*' -C "$REPO" archive "${REF[$k]}" tiny | tar -x -C "$B/$k" || { echo "$k archive 실패"; exit 2; }
    make -C "$B/$k/tiny" >/dev/null 2>&1 || { echo "$k 빌드 실패"; exit 2; }
    # exec이 이어지므로 $!가 곧 tiny의 pid다
    (cd "$B/$k/tiny" && exec taskset -c "$SERVER_CPUS" ./tiny "${PORT[$k]}" </dev/null >/dev/null 2>&1) &
    PID[$k]=$!
done
trap 'pkill -x tiny' EXIT
sleep 1
for k in "${NAMES[@]}"; do
    [ "$(cat /proc/${PID[$k]}/comm 2>/dev/null)" = tiny ] || { echo "$k pid ${PID[$k]}가 tiny가 아님"; exit 2; }
done

# 프로세스 전체(모든 스레드)의 utime+stime, 단위 tick
cpu_ticks() { awk '{print $14 + $15}' "/proc/$1/stat"; }

ipn=2
next_ip() { echo "127.0.0.$ipn"; ipn=$(( ipn % 250 + 2 )); }

for k in "${NAMES[@]}"; do
    curl -s -o /dev/null "http://127.0.0.1:${PORT[$k]}/$FILE" || { echo "$k 응답 없음"; exit 2; }
    taskset -c "$AB_CPU" ab -q -r -t 3 -n 100000000 -c 10 "http://$(next_ip):${PORT[$k]}/$FILE" >/dev/null 2>&1
done

total=$(( $(wc -w <<<"$CS") * REPEAT * ${#NAMES[@]} ))
echo "$FILE, 측정당 ${DUR}초 x ${REPEAT}회, 측정 $total번, 예상 약 $(( total * (DUR + REST + 1) / 60 ))분"
echo "method,c,run,rps,mean_ms,server_cpu_pct,ab_cpu_pct,failed,non2xx" >"$OUT"
done_n=0
for c in $CS; do
    for r in $(seq 1 "$REPEAT"); do
        for k in $(printf '%s\n' "${NAMES[@]}" | shuf); do
            sleep "$REST"
            t0=$(cpu_ticks "${PID[$k]}"); w0=$(date +%s.%N)
            out=$(/usr/bin/time -f "ABCPU %P" taskset -c "$AB_CPU" ab -q -r -t "$DUR" -n 100000000 -c "$c" \
                  "http://$(next_ip):${PORT[$k]}/$FILE" 2>&1)
            t1=$(cpu_ticks "${PID[$k]}"); w1=$(date +%s.%N)
            scpu=$(awk -v a="$t0" -v b="$t1" -v s="$w0" -v e="$w1" -v t="$TCK" 'BEGIN{printf "%.1f", (b-a)/t/(e-s)*100}')
            g() { awk "$1" <<<"$out"; }
            line="$k,$c,$r,$(g '/^Requests per second/ {print $4}'),$(g '/^Time per request.*\(mean\)/ {print $4}')"
            line="$line,$scpu,$(g '/^ABCPU/ {sub("%","",$2); print $2}')"
            line="$line,$(g '/^Failed requests/ {print $3}'),$(g 'BEGIN{n=0} /^Non-2xx/ {n=$3} END{print n}')"
            echo "$line" >>"$OUT"
            done_n=$((done_n + 1))
            printf '[%3d/%d] %-10s c=%-2s run %d: %s\n' "$done_n" "$total" "$k" "$c" "$r" "$line"
        done
    done
done

python3 - "$OUT" <<'EOF'
import csv, statistics as st, sys
rows = list(csv.DictReader(open(sys.argv[1])))
cs = sorted({int(r["c"]) for r in rows})
print()
print(f'{"c":>3} {"방식":<10} {"req/s 중앙값":>12} {"최소":>8} {"최대":>8} {"CV":>6} {"서버CPU%":>8} {"abCPU%":>7} {"실패":>4}')
for c in cs:
    for m in ["select", "threadpool"]:
        g = [r for r in rows if r["method"] == m and int(r["c"]) == c and r["rps"]]
        if not g: continue
        rps = [float(r["rps"]) for r in g]
        cv = st.pstdev(rps) / st.mean(rps) * 100
        sc = st.median(float(r["server_cpu_pct"]) for r in g)
        ac = st.median(float(r["ab_cpu_pct"] or 0) for r in g)
        fail = sum(int(r["failed"] or 0) + int(r["non2xx"] or 0) for r in g)
        print(f'{c:>3} {m:<10} {st.median(rps):>12,.0f} {min(rps):>8,.0f} {max(rps):>8,.0f} {cv:>5.1f}% {sc:>8.1f} {ac:>7.1f} {fail:>4}')
    print()
EOF
echo "원본: $OUT"
```
